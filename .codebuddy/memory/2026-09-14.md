# 2026-09-14

## 排查「打开历史窗口滚动时鼠标/滚动延迟」的卡顿原因（未改代码）
用户现象：打开历史列表后滚动，指针/滚动明显延迟；**最严重的是刚打开后的 1~10 秒**。

### 实测数据（临时诊断程序，复用项目源码 + 真实历史）
- 历史 200 条（上限）；类型：text 175 / url 12 / image 11 / file 2。
- `UserDefaults.standard["clipboardHistory"]` 是**单个 60 MB blob**（base64 图片在内）：
  - JSON 解码 200 条 = **914 ms**（启动时 `loadHistory()` 就干这件事）；
  - 每次剪贴板变化 `saveHistory()` 在主线程重新编码 60 MB（同量级），还会把 60 MB 交给 cfprefsd。
- `showWindow` → `updateItemViews()` 同步创建 200 张卡片 = **227 ms**：文档视图宽 **38032 pt**、卡片 200 张、每张 6 个子视图（合计 1200），其中 **每张卡片一个 NSVisualEffectView（.withinWindow 毛玻璃）= 200 个**，每张卡片 layer 还带 shadow（无 shadowPath）。
- 图片是原分辨率塞进 `layer.contents`：11 张共 **10.3 Mpx ≈ 39 MB 纹理**，最大 852x1752，卡片实际只有 160x90。
- 卡内文本最长 **7005 字**，被整段塞进 `maximumNumberOfLines = 0` + wrap 的 NSTextField。
- 程序化滚动实测（机器后台同时有 Comet 浏览器 ~100% CPU、WindowServer 50~80%、GPU 20~50% 的噪声）：
  - 现状：**30~80 帧/秒**（120 Hz ProDisplay），单步主线程 p50 ≈ 6~7 ms（扣除 1/120 s 等待），**最大卡顿峰值 60~214 ms**；
  - 交替 A/B（窗口阴影 / 窗口背景毛玻璃 / 卡片毛玻璃 各自开关）**未得到可辨识差异**，被后台浏览器噪声淹没 —— 结论只能定性。

### 代码层面确定的成本点（与现象对应）
1. 打开瞬间同步建 200 张重卡片 + 首次光栅化：200 个 backdrop 毛玻璃层、1200 个 layer、11 张大图纹理、200 个 layer 阴影。
2. 窗口 `isOpaque=false` + `backgroundColor=.clear` + `hasShadow=true` + 全屏宽 → 内容每帧变化都要由 WindowServer 重算窗口阴影。
3. 窗口背景 `.behindWindow` 毛玻璃（全宽 1728x217 pt）在窗口可见期间是"活"的，背后内容动一下就重算。
4. `HorizontalScrollView.scrollWheel` 手写滚动：每个滚轮事件立即 `contentView.scroll` + `reflectScrolledClipView`，无合并/节流。
5. 11 张大图原分辨率当 layer.contents，每帧被缩放合成；最长 7005 字的文本按 wrap 多行布局。

### 修复方向（按收益排序，待用户确认后实施）
① 只创建可见卡片（懒加载/视图池复用）而不是一次 200 张；② 卡片背景改用半透明纯色 layer（去掉 200 个 NSVisualEffectView）；③ `layer.shadowPath` 或去掉卡片阴影 + `window.hasShadow = false`；④ 图片先降采样出缩略图再当 layer.contents；⑤ 预览文本截断 + 限制行数；⑥ 历史别放 UserDefaults（60 MB），改文件/SQLite 并在后台队列编解码。

### 现场采样结果（决定性证据，每秒 app/WindowServer/GPU）
用户补充：**鼠标在历史窗口上方移动时延迟最严重，移开就好**。

- 基线（历史窗口未打开，15:21:47~15:22:47）：app 0%，**WindowServer 5~28%，GPU 0~22%**。
- 复现（15:22:51~15:22:54 打开窗口 + 鼠标在窗口上移动/滚动）：
  - app 峰值 **17.8%**（一次，即建 200 张卡片），随后 4.7 / 2.0 / 2.9%（App 线程数 5→13）；
  - **WindowServer 85 / 82.5 / 69.8 / 67.4%**；
  - **GPU 0 / 49 / 46 / 49%**；
  - 15:22:55 起 app 回到 0%，WS 回落 24.9%→12.4%。
- 结论：**瓶颈是窗口合成（WindowServer/GPU），不是 App 自身逻辑**（App 只占 ≤18%）。光标由 WindowServer 合成，WindowServer 逼近饱和 → 指针本身延迟；鼠标在窗口上方时还要额外做命中/光标/合成，所以只有压在窗口上才明显。代码里**没有任何 mouseMoved/TrackingArea/toolTip 处理**（grep 0 命中），App 侧那点 CPU 全是 AppKit 机械开销。
- 触发根源仍是窗口的渲染配置：200 个 `.withinWindow` 实时 backdrop 毛玻璃层 + 200 个 layer 阴影（无 shadowPath）+ 全宽 `isOpaque=false` + `hasShadow=true` + `.behindWindow` 全宽毛玻璃 → 只要有指针/滚动这类局部变化，就要重新合成整块 1728x217 的窗口区域。

## 修复实施完成（2026-09-14 下午）
用户确认方案：卡片背景全部改半透明纯色层 / 窗口背景毛玻璃保留（只关系统阴影）/ 卡片改视图池复用 / 历史存储本期一起重构。

### 代码改动
- 新增 `HistoryStore.swift`（元数据 `history.json` + `images/<uuid>.dat`，串行后台队列，幂等迁移 + 回读校验后删旧 key）与 `ThumbnailCache.swift`（ImageIO 降采样 360px + NSCache + 后台队列）。
- `ClipboardItem`：去掉 `Codable`（持久化交给 HistoryStore 的 Record/LegacyItem），新增 `imageFileName`/`imageByteCount`/`imageDataLoader`（按需读盘）/`releaseInMemoryImageData()`/`previewTextForDisplay`（截断 400 字）/静态 DateFormatter/`cachedIcon`。
- `ClipboardManager`：UserDefaults 读写全部换成 HistoryStore，异步加载 + `.clipboardHistoryDidLoad`，去重比较改用 `imageByteCount`。
- `HistoryWindowController`：池化（`cardPool` + `rebuildCardPool()` + `refreshVisibleCards()` + `cardX(for:)`，池视图自持 `index`，bounds 变化通知 `queue: nil` 同步刷新）；`hasShadow=false`；删除/加载完成/外观变更重建池；`handleKeyDown`/`deleteItem` 用 `items.count`。
- `ClipboardItemView`：背景改普通 layer 半透明纯色（选中=蓝底+蓝描边，透明度滑块照旧）、`shadowPath`、缩略图异步、预览限 6 行、删除 `PassthroughVisualEffectView`。
- `AppDelegate`：订阅加载完成通知刷新已打开窗口；`build.sh` 加入两个新文件。

### 补记：残留诊断窗口
- 用户发现屏幕底部还有一个历史列表。原因是我那个 v4 诊断程序（`bench_new`）的滚动循环里**每秒把起始时间 `t` 重置**，导致 `while 当前时间 - t < 20` 永远不成立、程序不退出，从 15:41 起一直顶着一个 1728x217 的窗口在滚（pid 85719）。
- 已 `pkill -x bench_new`，并用 `CGWindowListCopyWindowInfo` 确认底部已无残留窗口；同时收掉仍在跑的 `watch.sh` 后台监控（它会把被删掉的 watch.log 重新创建出来）。
- 教训：以后写一次性诊断程序，外层循环用「累计的绝对截止时间」计时，不要在打印统计时重置计时起点；退出前最好显式 `exit(0)`。
